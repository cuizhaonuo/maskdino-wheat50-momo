## 判定（按预注册）

**预注册判定：「机制未启动」。** 机制门 M1 没过：L1-only 配对下 `ŷ^k` 的误差为 **0.0189**，线是 < 0.0158。
按预注册规则，M1 不通过时主判据「不能用来评价 KMO」。

| 判据 | 实测 | 线 | |
|:--|--:|--:|:--:|
| **M1** L1-only 配对下 mean\|ŷ^k − y^k\|（终） | **0.0189** | < 0.0158 | ❌ |
| M2 推翻率（终） | 21.4% | ≥ 1% 才不算空操作 | ✅ 非空操作 |
| 主判据 `matched_F1@8` 峰值 | **0.5962** | ≥ 0.5883 | ✅（数值） |
| 主判据 `matched_F1@8` 末值 | **0.5954** | ≥ 0.5818 | ✅（数值） |
| 护栏 `segm/AP` 峰值 | 74.21 | ≥ 73.17 | ✅ |
| 护栏 `count_MAE_spike` 峰值 | 3.98 | ≤ 4.19 | ✅（但末值 4.22，见「计数」一节） |

端到端提升是真实观测到的：基线 +0.024，是 +0.01 这条线的 2.4 倍。但按预注册写死的规则，
**不能把它归功于 KMO 的上下文机制。** 事后分解（下文，非预注册）显示机制其实部分起作用了，
是 M1 这条判据本身设计得过严。这一点作为预注册设计的教训记下，**不改变判定**。

## 机制诊断（M1 / M2，预注册）

工具：`myscripts/backup/vis_process/kmo_match_diag.py`。在 mini train 上以训练态做前向
（不求梯度，100 个 batch，seed 0，1586 个有点实例 / 24766 个点），只看最后一层 decoder 的内层匹配，
在同一份预测上分别求 KMO 配对与 L1-only（Eq.2）配对。

| | iter 2999 | 最终 | 预注册线 |
|:--|--:|--:|:--|
| **M1** L1-only 配对下 mean\|ŷ^k − y^k\| | 0.0218 | **0.0189** | < 0.0158 ❌ |
| KMO 配对下（即训练日志口径） | 0.0213 | 0.0184 | 仅参考（有选择偏差） |
| **M2** 推翻率 | 25.5% | **21.4%** | ≥ 1% 才不算空操作 |
| M2 换 tie 率 | 0.57% | 0.38% | |
| 推翻时 Eq.2 代价差（中位） | 0.065 | 0.055 | |

- **KMO 不是空操作**：最终仍有约五分之一实例的配对被它推翻。smoke 阶段 iter 60 时推翻率是 99%，
  到 iter 2999 降到 26%，早期噪声已大幅收敛。
- **推翻都发生在近乎打平的候选之间**：推翻时 Eq.2 代价差中位 0.055。除以坐标权重 5，
  折合 L1 距离约 0.011（框相对），约为穗框尺寸的 1%。这正是论文设想的工作区间：用上下文替 L1 打破平局。

### 事后分解（**非预注册**，看到 M1 结果后才加）

M1 把两件事混在了一起：`ŷ^k` 能不能估准「这个穗整体的近邻尺度」，以及能不能估出「穗内各小穗之间的差异」。
**只有后者告诉匹配器「哪个槽该配哪个小穗」**：整体偏移较大时，|c + v_j − y_i| 的符号固定，KMO 项会拆成「逐槽偏置 + 逐列常数」，只影响挑哪些槽、不再区分穗内的配对。于是给诊断工具加了拆分：

| | iter 2999 | 最终 |
|:--|--:|--:|
| 逐实例水平偏差 mean\|mean(ŷ^k) − mean(y^k)\| | 0.0162 | **0.0121** |
| **实例内 Pearson r**（ŷ^k 与 y^k 各减去本实例均值后） | 0.41 | **0.47** |
| 实例内 std：ŷ^k / y^k | 0.0132 / 0.0235 | 0.0132 / 0.0235 |
| 同样本 oracle 逐实例常数 MAE | 0.0158 | 0.0158 |

- **M1 没过，主要是因为水平偏差（0.012），不是因为穗内没有信号。** 实例内 r = 0.47，
  头确实学到了一部分穗内的近邻结构。r≈0.47 的线性预测器，其 std 应收缩到约 0.47 × 0.0235 ≈ 0.011，
  实测 0.013（std 比 0.56 vs r 0.47），接近「收缩但有信息」的预测器应有的水平。
- 同样本 oracle 值（0.0158）与离线统计的 `MAE_inst` 完全一致，说明判据线本身标定得没问题；
  问题出在判据的形式：它要求头赢过一个**知道每个穗真实中位数的 oracle**，比它想检验的
  「槽之间有没有有效差异」严得多。
- **教训**：以后给辅助预测量写机制门，应当把「组间水平」和「组内信号」分开检验
  （例如预注册组内相关系数的下限），不要用一个 MAE 同时考两件事。

## 计数：两臂都系统性多数，差异主要是标定偏移

最终评估的逐穗计数（`inference/spikelet_pair_counts.csv`，阈值 0.35）：

| | 穗数 | MAE | 偏差（预测 − GT） | 多数 / 相等 / 少数 | \|差\| ≥ 5 |
|:--|--:|--:|--:|:--|--:|
| 基线 | 558 | 3.88 | **+3.70** | 90.7% / 3.4% / 5.9% | 37.5% |
| KMO | 566 | 4.22 | **+4.09** | 92.9% / 3.4% / 3.7% | 45.1% |

两臂都有九成以上的穗被多数（平均预测约 20 个点，GT 为 15.9）。**`count_MAE_spike` 在 0.35 这个固定阈值下
主要反映的是阈值标定**，KMO 多出的 0.34 MAE 几乎等于它多出的 0.40 偏差，即存在性头整体略偏高。
按 [point-canonical-order](../ideas/point-canonical-order.md) 的做法，**必须先做阈值扫描、再比 best-vs-best**，
才能判断这是不是真的退步。预注册护栏看的是峰值（3.98 ≤ 4.19，通过）；末值 4.22 则过不了同一条线，特此记录。

## 归因限制与下一步

本次提升不能按预注册归功于 KMO，理由有三：
(1) M1 判定机制未启动；
(2) KMO = 新的匹配代价 + `ŷ^k` 辅助回归损失，两者绑在一起；
(3) 两臂各只有一个种子。

还有一个值得注意的信号：**`bbox/AP` 末值 +1.97**。内层点匹配并不直接作用于框，
这更像是辅助损失对共享 decoder 起了多任务正则作用，或者就是种子差异。

建议按顺序：

1. **两臂各补一个种子**（各约 7 h，可在同一张 A100 上并发）。这是给 +0.024 和 +1.97 标出误差棒的唯一办法。
2. **消融 `COST_POINT_KNN_WEIGHT=0`**（只保留辅助损失，不改配对），把「配对改变」和「多任务正则」拆开。
3. 两臂的 `count_MAE_spike` 做**阈值扫描**，比 best-vs-best。
4. 若 1、2 之后效应仍在，再上 2092 图全集，开 `full/kmo-matcher` 与 p30 对照。
