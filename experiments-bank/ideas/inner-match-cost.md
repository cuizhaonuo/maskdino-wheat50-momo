# 想法：内层点匹配被 `COST_POINT_*: 0.0` 关掉了

状态：**部分成立** ｜ 提出 2026-08-21 ｜ 验证于
[exp-2026-08-21-innercost](../experiments/exp-2026-08-21-innercost.md)

## 现象（来自 baseline）

`loss_point_cls` 16.25 → 0.278（降 98%），`loss_point_coord` 1.90 → 1.68（降 11%，噪声级）。
点级 F1 从第 800 iter 起完全走平。可视化里预测点整齐压在每个穗的**中轴线**上排成一列，
GT 小穗却分布在穗的左右两侧。

## 假设

`criterion.py:333` 的内层匹配代价 `C = point_cost_coord*cost_coord + point_cost_class*cost_class`，
两个权重都是 0 → `C` 全零 → `linear_sum_assignment(zeros)` 返回**平凡分配**
（已实证：`[0,1,2,…] → [0,1,2,…]`）。即第 k 个预测点槽被硬性指派给标注顺序的第 k 个
GT 小穗，**与距离完全无关**。GT 标注顺序沿穗轴左右交替，若起始边不一致，slot k 的目标
就在左右间跳；L1 下的最优解是中位数 → 中轴线。

原注释写的是"使外层匈牙利匹配与 Stage1 一致"，但这两项只作用于**内层**；
外层 query↔实例匹配走 `matcher.py`，本就不含小穗点项（那里的 `num_points` 是 PointRend
的 mask 采样点）。原意图本就自动满足，置 0 只是误伤了内层。

## 修法

```yaml
COST_POINT_COORD_WEIGHT: 5.0    # 原 0.0
COST_POINT_CLASS_WEIGHT: 2.0    # 原 0.0
```

## 预期（跑之前写死）

- `loss_point_coord` 持续下降至 **1.0 以下**
- `F1@5 ≥ 0.3`、`matched_F1@8 ≥ 0.5`
- 可视化中预测点离开中轴线
- `count_MAE_spike` 不变差（≤ 2.5）
- 判否线：**若 `F1@5` 到不了 0.2，说明塌陷另有原因**

## 结论

**机制证实，幅度预测失败。** 六项预期中两项达成：

| 预期 | 实测 | |
|:--|:--|:--:|
| `loss_point_coord` < 1.0 | **0.3513** | ✅ |
| 点离开中轴线 | 确认，已铺到穗的左右两侧 | ✅ |
| `F1@5 ≥ 0.3` | 0.094（默认阈值）/ 0.146（最优） | ❌ |
| `matched_F1@8 ≥ 0.5` | 0.264 / 0.376 | ❌ |
| `count_MAE_spike ≤ 2.5` | **8.20**（baseline 2.30，反而恶化） | ❌ |
| 判否线 F1@5 ≥ 0.2 | 最高 0.146 | ⚠️ 未达到 |

按判否线，本假设不能算完全成立。但机制本身是确凿的：

- baseline 的 F1@8（.1629）**低于**"把 N 个点沿框中轴等间距排开"这条平凡解（.1729），
  即它确实什么都没学到；修复后 .2868，超出该参照 66%。
- 同点数下（`POINT_THRESHOLD=0.28`，3799 点 vs baseline 3382）各档 F1 提升 43%~76%。

**正确的读法是：内层匹配退化是第一个瓶颈，但不是唯一的。** 修好它之后暴露出两个新瓶颈，
见 [exp-2026-08-21-innercost](../experiments/exp-2026-08-21-innercost.md) 的「新瓶颈」一节。
